### CI red on purpose (run #2, 2026-10-31, commit `a96003d`)

R1 pushed on a throwaway branch. The hook let it through (L0 8 of 8 then; lint cannot see
a logic bug). CI failed **at L1 only**; setup, the Sail sha256 checks and L0 all passed.

- **lockstep**: `t01` first difference at `instr=0x40110233` (`sub x4, x2, x1`): Sail
  `x4 <= 0x0000000a`, core `0x0000001e` — 20 − 10 against 20 + 10. `t03`, `t04` diverge at
  the same instruction; `t06` at `sub x12, x11, x10` with equal operands (Sail 0, core
  `0x88`). 3 of 7 agree.
- **harness checksums**: `t03`, `t04`, `t06` FAIL, e.g. `expected 0x00fe3a2e, got 0x00fe40e2`.
- **ACT4**: 0 of 47. `I-sub-00`: `sub x31, x0, x28`, expected `0x52a9a7c1`, got
  `0xad56583f` — x28 instead of −x28. 44 others report a trap-count mismatch; that
  ACT4's own self-check code uses SUB is T4, consistent with the evidence, not measured.
- **coverage**: `INCOMPLETE: 50 run(s) failed, 6 of 56 merged`, and all three targets
  BELOW. **classify**: 1,733 unmatched — a consequence of the incomplete merge, so not
  counted as a separate detector.

Three independent detectors caught it: Sail, the harness checksums, ACT4.

## 4. Defects found in the verification infrastructure

### 4.1 Lockstep passed with Sail missing — the third silent pass in that script

`run_lockstep.sh` sent Sail's output and exit status to `/dev/null` and never deleted
the previous run's trace. L1 mutant S1 (Sail missing) was **MISSED** in the first L1
mutation run (6 of 7, 2026-10-30). Measured directly, one variable at a time:

| Case | Result |
|---|---|
| A: `SAIL=/nonexistent`, default `WORK` holding an old trace | `1 of 1 programs agree`, **exit 0** |
| B: same, empty `WORK` | `FileNotFoundError` in `compare.py`, exit 1 |

So the old trace, not the missing Sail, decided the verdict. Same shape as `0018`
(harness verdict discarded) and `0028` (no arguments compared nothing). Provenance
notes were added to `0015` and `0018`; no recorded number changed, because Sail was
installed throughout (T4: nothing in the record suggests otherwise).

**The first fix was wrong, and my measurement was why.** It required Sail to exit 0,
based on probe C, which ran only `t01`. Applied, it failed four correct programs:
`t03`-`t06` (exit 1, trace present). Sail's termination, measured on all seven
(2026-10-30):

| Program | Sail output | Exit |
|---|---|---|
| `t01`, `t02`, `t07` | `SUCCESS` | 0 |
| `t03`, `t04` | `FAILURE: 16661038 (0x00fe3a2e)` | 1 |
| `t05` | `FAILURE: 44353573 (0x02a4c825)` | 1 |
| `t06` | `FAILURE: 1124066658 (0x42ffe562)` | 1 |

`t03`-`t06` store a checksum in `tohost`, which Sail reports as a failure code. `t01`
was a test value where "exit 0" and "Sail completed correctly" agree — failure mode #1,
in my own measurement. The rule that shipped: a non-empty trace **and** exactly one
termination line **and** (`SUCCESS` with exit 0, or `FAILURE:` with exit non-zero).
S2-S5 test each way that rule could be fooled.

Two observations, not acted on: the printed code is the stored value with bit 31
cleared in all four cases (`0x82a4c825` → `0x02a4c825`, `0xc2ffe562` → `0x42ffe562`);
mechanism not investigated. And `sw/tests/htif.S`'s comment says a failure is
`(code << 1) | 1`, but `TEST_END` writes the value unshifted. The comment is stale.

### 4.2 `run_coverage.sh` exited 0 below target

Its exit status covered missing runs but not the §5.3 targets. Fixed in `6da78f7`; T1
is the mutant. `0028`'s numbers do not change — every target was `MET` — and `0028`
carries a provenance note. Run #2 is its first real catch.

### 4.3 Two Sail builds report the same version

The `0.13.1` tag build (binary `b83c230e…`) and the dated release
`2026-08-17-8f91355` (binary `55de5754…`, tarball `095dcdb5…`, 2,571,363 bytes) both
print `0.13.1` (measured 2026-10-30). Every lockstep result and the ACT4 ELF set were
produced with the second, the one `0015` names. CI downloads it and checks both hashes;
`check-sail` (L0) requires the binary hash locally. Tested here against both real
binaries: release passes, tag build fails.

## 5. Known limits

- **Verilator exempts `*unused*` names from UNUSED warnings** (`--unused-regexp`
  default, T2 man page, T1 measured: the first lint mutant, `mut_unused_q`, passed lint).
  An unused signal so named is invisible to L0 lint. Recorded; nothing changed.
- **The pragma scan knows a fixed prefix list** (`verilator`, `synthesis`, `synopsys`,
  `pragma`, `translate_off/on`, `coverage`, `cadence`, `ambit`, `xilinx`, `altera`).
  A directive for another tool passes.
- **`sail-guard` runs in L0, not in lockstep**, so the S2-S5 wrappers still reach the
  verdict rule. L1 run on its own with a different `SAIL` is unguarded. Confirmed by
  the 8a re-run: S2-S5 still fail at `lockstep`, not at the guard.
- **The container digest appears twice in `ci.yml`** (the `container:` line and the
  cache key); a comment says they must match, nothing checks it.
- **The hook checks only the tip of each pushed ref**, and `--no-verify` skips it.
  CI is the gate.
- **apt packages other than binutils are recorded per run, not pinned.** The digest
  pin fixes the base image; `apt-get update` still reads today's archive.
- **The ACT4 ELFs are built off-CI** (GCC 16.1.0 is not in the container). The manifest
  binds them to the five config files that produced them, which E4-E6 test; Sail's
  binary hash goes into the manifest at the next regeneration.
- **Not in CI:** formal, slang lint, UVM env 7 (ADR-0009).
- Cosmetic: the reset-twice harness prints `Kharness: coverage written…`, locally and in
  CI. Not investigated.

## 6. My errors on the way

Recorded because they are the same failure modes the project ranks, made by the reviewer.

1. **The first lint mutant could not fail** (2026-10-29): named `mut_unused_q`, it hit
   Verilator's `*unused*` exemption and passed lint. 14 of 15. Renamed
   `mut_dangling_q`; 15 of 15. Failure mode #1.
2. **"33 MB of ACT4 ELFs"** was a `du` of the whole ACT4 folder. The ELF set is
   8,475,952 bytes (4,542,752 compressed). The figure reached the `mutate_l0.py`
   docstring and was corrected in `835e265`. Failure mode #3's cousin: a number not read
   from the thing it describes.
3. **The first lockstep fix rested on one program** (§4.1). Failure mode #1.
4. **The first `ci.yml` downloaded the `0.13.1` tag**, a different binary from the one
   every result used. Caught before any push by comparing the two binaries' hashes
   (2026-10-30); the workflow now pins the dated release and checks both hashes.
5. Reading the ci3c log, I filtered compile lines with `grep -v` before reading them in
   full (§2.4). I then scanned the rare lines; nothing was hidden, but the order was wrong.
